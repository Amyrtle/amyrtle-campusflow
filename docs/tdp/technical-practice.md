# 用 PostgreSQL 事务连接活动报名与签到

校园活动系统的关键问题往往出现在最后几个名额和重复扫码时。页面显示还有一个名额，并不意味着两个并发请求可以同时获准；扫码显示成功动画，也不等于数据库只保存了一次签到。

CampusFlow 将这些判断放在服务端和 PostgreSQL 中。报名请求携带幂等键，事务内检查活动状态和时间窗口，再执行受容量保护的写入。唯一约束区分正常重试和新报名。签到凭证使用不可预测的秘密值，数据库只保存摘要，二维码不直接携带参与者称呼或其他个人信息。

签到时先验证登录身份、组织成员关系和活动分配，再验证凭证属于当前活动。事务和唯一约束保证同一凭证只贡献一个签到人数。统计直接读取有效报名和签到记录，在零报名时明确返回零签到率。

AI 也通过相同的服务边界进入业务。模型只提供可编辑建议，Zod 校验结构，用户确认后创建草稿，再单独决定是否发布。缺少预算或地点时保留待确认项。未配置真实模型时使用带有清晰标识的模板，不能把模板伪装成模型调用。

本地开发使用 PGlite 保留 PostgreSQL 的查询和事务语义，云端目标是 CloudBase PG。两者仍有部署边界：网络认证、数据库角色、RLS、TLS、资源配额和真实设备扫码都需要在目标环境重新验证。本文描述实现思路；已执行测试及实际云端状态以仓库中的进度和测试报告为准。
